## 0. 结论摘要（TL;DR）

**一句话结论**：问题诊断是对的，核心反丢数不变量也选对了。但真实规模只是「1 个人、3–5 台设备、每天几百条修改」，方案却叠了约 50 个具名机制。其中相当一部分 (a) 和第一目标「永不丢数」无关，(b) 反而**引入了新的丢数或泄密路径**，(c) 还有多处规范互相矛盾。应当先修正、裁剪、重排，再写代码。

**最关键的 7 个发现**：

| # | 严重度 | 发现 | 一句话 |
| --- | :---: | --- | --- |
| F-01 | 🔴 | Tier 2 AAD 绑定 `op_id`，本地 API 却不传 `op_id` | 加密块可能「写入即永久无法解密」；AAD 在两份文档里定义不一致 |
| F-02 | 🔴 | 快照/GC 截断历史后，`SPAN_PATCH` 基底与因果判定无定义 | 快照引导的设备可能永远物化不出某个分支，违反强最终一致 |
| F-03 | 🔴 | HLC 漂移「服务端钳制」做不到，客户端「拒收」会导致分歧 | HLC 在盲信封里；时钟快 6 分钟的设备，它的修改会被别的设备丢弃或卡住同步 |
| F-04 | 🔴 | `purge_op_ids` 等「抹除原语」削弱了 Anti-Wipe 不变量 | 盲服务端无法校验，任一持 Token 的客户端（含被注入的 Agent）都能远程置空历史 |
| F-05 | 🔴 | 密钥生命周期本身就是和 iCloud 同量级的丢数源 | 轮换 SMK 后恢复词失效；旧 SMK 何时删除没定义；有两套 24 词；从没做过恢复演练 |
| F-06 | 🔴 | 「可靠备份」和「保证删除」同时被承诺 | 3 年归档、K=5 快照、Lock-Wins 明文分支、PITR 覆盖瞬态剪贴板，都和「擦除」承诺冲突 |
| F-07 | 🔴 | T5「密码学级硬隔离」对主动型同 UID 攻击者不成立 | 攻击者可以篡改用户可写的二进制或 shell rc，等你下次解锁 |

**最重要的 5 条建议**：

1. 把 ADR 从「已最终拍板」**降级为「提议中（Proposed）」**，先做 1–2 周的技术 spike 拿到证据，再冻结（§6.1）。
2. 编码前先修完 F-01～F-07 的规范矛盾。
3. **裁剪或推迟**：`SPAN_PATCH`、R2 多代快照 + CAS、DO 滑动窗口 GC、`purge_op_ids`、`vault_keys` 同步表与碎纸、WebAuthn PRF 多槽位、瞬态剪贴板、自升级子系统、Plane B 评测与自动爬山（§4）。
4. **重排路线图**：第一个里程碑就要包含 E2EE 同步，做成一个能让你**卸载 Heynote + iCloud** 的最小闭环（§6）。
5. 把「**丢钥匙**」和「**逻辑 bug 扩散到所有副本**」当成和 iCloud 同等级的丢数源来设计：一份统一恢复包 + 自动化恢复演练 + 一份和同步代码无关的本地独立备份或明文导出。

## 1. 第一性原理：从不可再分的事实出发

### 1.1 不可再分的事实

| 事实 | 推论 |
| --- | --- |
| 用户只有 1 人，设备 3–5 台 | 没有多租户，也没有实时协作。真正的并发冲突只有「同一块在两台设备上同时离线编辑」，频率极低 |
| 写入量：文档口径 300–500 ops/日 × ~1.2 KB ≈ **0.6 MB/日 ≈ 220 MB/年** | 按文档给出的 1 GB DO 上限，**不做任何 GC 也能撑 4 年以上**；全量语料在 MB 量级，传全量状态、做全量快照都很便宜（附录 A） |
| 痛点根因 = 网盘文件同步 + 整文件覆写 + 把空状态当权威 | 把这三点都消除，这一类事故就消失了。其余机制都只是优化 |
| 丢数据**不可逆**，体验欠佳**可迭代** | 优先级应按「不可逆程度」排序 |
| iOS 只能用 PWA（或原生 App），没有后台同步，存储可能被驱逐；macOS 全局热键需要原生壳；Linux 上 WebKitGTK 有风险 | 平台约束决定交付形态，原型验证必须早做 |
| 代码 0 行，规范约 3,400 行，全部出自同一天的 7 个提交，且标注「已冻结」 | 文档里所有性能、体积、行数数字都是**估计而非测量**；「冻结」缺乏证据支撑 |

### 1.2 目标函数（按不可逆程度排序）

- **G1 永不静默丢数**：涵盖同步 bug、**丢钥匙**、误操作、平台驱逐、逻辑 bug 扩散。
- **G2 随手即记、随叫随到**：100 ms 内唤出，CLI 秒回。
- **G3 多端可得**：桌面之间实时同步；手机至少能读、能复制、能追加。
- **G4 秘密不落明文、不以明文进云端。**
- **G5 Agent 可读写**（通过 CLI）。
- **G6 Heynote 式分块与格式化，Markdown/Mermaid 渲染。**
- 约束 **C1**：一个人能长期维护（复杂度预算）；**C2**：\$0/月。

### 1.3 审查准则

对每个机制追问：

- **Q1**：它服务哪个 G？删掉后，哪个 G 会被**可观测地**破坏？
- **Q2**：它引入了哪些**新的失败模式**，尤其是新的丢数或泄密路径？
- **Q3**：在当前规模下，有没有更便宜的等价物？能不能等数据触发时再做？

## 2. 方案做对了的部分（应保留）

以下设计直接对准 G1/G4，成本低、论证扎实，建议原样保留：

1. **根因诊断准确**：把 Heynote + iCloud 的丢数归结为「网盘文件同步 + 整文件覆写 + 空态被当作权威」（[architecture-proposal.md §1](../docs/architecture-proposal.md)），并由此推出 4 条 Anti-Wipe 不变量。
2. **Bootstrap Gate**：未完成首次引导的设备不得修改远端已有实体（[sync-protocol.md §3](../docs/sync-protocol.md)）。这一条直接封死了 Standard Notes 式事故。
3. **非明文状态在类型层面隔离**：`Unhydrated` / `DecryptFailed` 无法构造 `UPDATE`。
4. **零字节熔断**：外部格式化器与 CLI 空 stdin 默认拒绝写回，成本极低、收益极高。
5. **HTTP 为真相，WebSocket 只是提示**；强制 `redirect: "manual"`，校验 JSON 里的 `ack` 后才清 Outbox（[cloudflare-cloud-architecture.md §6 #1](../docs/cloudflare-cloud-architecture.md)）。这是来自真实事故的教训。
6. **`epoch` 变化时按 `op_id` 求集合并集，严禁先清表**（[sync-protocol.md §6](../docs/sync-protocol.md)）。
7. **Block-First 数据模型**：块是同步、加密、检索的最小单元。
8. **CLI 契约**：离线写成功返回 `0` 加 `sync_state`；`--expected-head` 乐观锁；摘要优先，保护 Token 预算；错误带 `hint`。放弃 MCP、改走 CLI 的决策合理。
9. **威胁模型里有不少诚实段落**：PWA 的「代码分发信任自有 CF 账号」，以及「`isatty` / `MYNOTE_ACTOR` 不是安全边界」。
10. **用确定性模拟（DST）给同步把关**：方向完全正确。
11. 外部依赖核验通过：Pele 确实存在（Obsidian 团队 2026-10 开源，MIT 协议，覆盖 Mermaid 12.1 内置图表类型）；DO 单语句 100 个绑定参数、30 天 PITR 均与官方文档一致（附录 B）。

## 3. 发现（Findings）

### 3.1 🔴 P0：正确性缺陷与自相矛盾

#### F-01 Tier 2 AAD 绑定 `op_id`，但本地 API 契约不传 `op_id`

- **证据**：
  - `MNV1` 的 AAD 是 `"MNV1" || 0x01 || block_id || op_id || kid`（[data-structures.md](../docs/data-structures.md) L282）。
  - `WasmVaultSession.encryptNewBlock(blockId, opId, …)` 和 `encryptExistingBlock(…, opId, …)` 都要求前端提供 `opId`（[interface-contracts.md](../docs/interface-contracts.md) L368–L371）。
  - 但 `POST /v1/local/blocks`、`PATCH /v1/local/blocks/:id`、`POST …/lock`、`POST …/resolve` 的请求体里**都没有 `op_id` 字段**（interface-contracts.md L198–L203）。
- **推演**：Daemon 只能自己生成 `op_id`，于是 AAD 对不上，这个加密块在**所有设备上永久 `DecryptFailed`**。缺陷恰好落在最敏感的数据上。
- **连带问题**：所有「沿用旧密文、产生新 op」的路径（例如 `RESOLVE --keep` 保留一个加密分支）都必须先解锁、再重新加密，而 Daemon 按设计永远做不到这一步。
- **线格式有两个版本**：AAD 在 [architecture-proposal.md](../docs/architecture-proposal.md) L440 写作 `"mynote-sync-v1" || …` / `"mynote-vault-v1" || …`，在 data-structures.md L271/L282 写作 `"MNS1" || 0x01 || …`。
- **建议**：
  - (a) 规定 `op_id` 由**执行加密的一方**生成并随请求提交，Daemon 必须原样使用；
  - 或 (b) Tier 2 AAD 去掉 `op_id`，改为绑定 `block_id || kid || content_nonce`，让密文能在不同 op 之间安全搬运。
  - 以 data-structures.md 为唯一定义，删掉 architecture-proposal.md 里的副本。

#### F-02 快照/GC 截断历史后，因果判定与 `SPAN_PATCH` 基底没有定义

- **证据**：
  - `SnapshotBodyV1` 只含物化状态，不含 op DAG（data-structures.md L296）。
  - `SPAN_PATCH` 必须在 `base_op_id` 对应的全文上应用，失配就「报错中止」（[sync-protocol.md](../docs/sync-protocol.md) L121）。
  - DO 30 天后执行 GC。
  - **本地 `sync_ops` 的保留策略在任何文档里都没定义**。
  - `step()` 的输入 `EngineSnapshot` 内容也没定义（sync-protocol.md L36）。
- **推演**：
  - 设备 A 离线期间，基于旧版本 P 对一个大块连续编辑，产生了 `SPAN_PATCH` 分支。
  - 设备 C 通过快照引导，只拿到当前主分支 H 的全文。
  - A 上线推送后，C 收到 `base = P` 的补丁，本地却没有 P 的全文，于是按规范中止。
  - 结果：C 永远看不到这个分支，B 却看得到。这违反 INV-SYNC-1（强最终一致），而且 A 的修改在 C 上是**静默缺失**的。
- **第一性原理**：只要「依赖历史的载荷（delta）」和「截断历史（GC/快照）」同时存在，就必须定义「基底拿不到」时怎么办。最便宜的解法是不用 delta。
- **建议**：
  - M1 只用 `FULL_ZSTD`（规模论证见 F-09）。
  - 如果将来必须用 delta：规定「分支上的第一个 op 必须是全量」「快照必须带上每个叶子的全文」。
  - 在 sync-protocol.md 补一节「历史截断下的因果判定」，并精确定义 `EngineSnapshot`。

#### F-03 HLC 漂移钳制：服务端做不到，客户端「拒收」会导致分歧或同步停滞

- **证据**：
  - sync-protocol.md L151 写的是「客户端与服务端均实施……拒绝接收」。
  - 但 `hlc` 被封在 `MNS1` 密文里，服务端看不到（sync-protocol.md §2.1）。
  - data-structures.md L51 规定客户端返回 `ClockDriftExceeded`。
- **推演**：假如一台手机的时钟快了 6 分钟，它产生的 op 会被所有其他设备拒收。
  - 如果拉取游标越过这条 op：它在这些设备上**永久缺失**，等于丢数。
  - 如果游标卡住：所有设备的同步一起停滞，直到时钟追上。
  - 规范对这两种情况都没有说明。
- **建议**：**永不因为时钟原因拒收 op**。按标准 HLC 算法，把远端 HLC 合并进本地时钟并告警即可。时钟偏差最多导致「时钟快的那台设备赢下 LWW」，不会丢数据（所有版本都保留）。删除「服务端钳制」的表述。

#### F-04 新增的「抹除原语」削弱了 Anti-Wipe 不变量

- **证据**：
  - `purge_op_ids` 允许任何持有 `device_token` 的客户端，把**任意** `op_id` 的 envelope 置为 `NULL`（[threat-model.md](../docs/threat-model.md) L113–L115）。服务端是盲的，无法校验这些 op 是否真的属于被加锁的块。
  - 同类的抹除路径还有：
    - DO GC 删行；
    - 快照 CAS 发布（`state_blake3` 由同一份客户端代码计算，只能证明**完整性**，不能证明**正确性**）；
    - `vault shred`；
    - `update --rollback` 恢复升级前的数据库（interface-contracts.md L164）。
- **第一性原理**：「Anti-Wipe by Construction」应当意味着「**不存在任何代码路径能让已提交的数据变得不可恢复**」。每多一个抹除原语，这个保证就从「构造性」退化成「依赖所有客户端实现都没有 bug」。
- **与 T5 叠加**：
  - Linux 的 Secret Service 不对同 UID 进程做按应用 ACL，被注入的 Agent 可以直接取得 SMK 和权限为 `0600` 的 `device_token`。
  - 拿到之后，它可以用 `purge_op_ids` 远程置空云端的活跃历史。
  - 威胁模型只讨论了「读取」，没有列出这条**破坏性**路径。
- **兜底形同虚设**：现有兜底是 R2 每日归档，但归档**不在任何自动恢复路径中**（引导流程 = 快照 + DO 增量），等于一份「从未演练过的备份」。
- **建议**：
  1. 删除 `purge_op_ids`，或只允许「人工交互、二次确认」的管理命令触发。事后加锁的诚实语义应当是「从此以后不再以明文保存」；对已经同步过的明文，提示用户**轮换该秘密本身**。对 Token 类秘密来说，轮换远比擦除历史有效。
  2. 把 R2 归档定义为「服务端只追加、客户端不可删除」的独立备份，提供 `mynote restore --from-archive`，并把恢复演练写进门禁。
  3. 本地增加一份和同步代码无关的独立备份（见 F-05、F-19）。

#### F-05 密钥生命周期本身就是一个与 iCloud 同量级的丢数源

E2EE 带进来一种新的丢数方式：**丢钥匙**。证据：

- SMK 可以由 24 词恢复词派生（architecture-proposal.md L447），但 `rotate-smk` 会生成全新的 `SMK_v2`（threat-model.md L197）。**轮换之后，旧恢复词恢复不了新数据**，而文档没有要求轮换时重新生成或打印恢复包。
- **旧 SMK 何时可以删除没有规定**：R2 归档和快照是用旧 SMK 加密的，轮换后一旦删掉旧 SMK，冷备就变得不可读。
- Vault 另有一套 24 词恢复码（architecture-proposal.md L453）。两套是不是同一套没有定义，用户到底要保管 1 份还是 2 份也不清楚。
- **没有恢复演练**：「全部设备丢失后，仅凭恢复材料能否恢复全部数据」从未被列为验收项。

**建议**：

- 用**一份恢复包**派生一个 Root Key，用它包裹一个随同步存储的**密钥环**（`keyring = { smk_v1, smk_v2, …, vkek }`）。
- 轮换只往密钥环里追加，不删除旧钥，除非用户显式选择「放弃旧归档」。
- 在 Plane A 新增门禁 **INV-RECOVERY**：从零设备出发，仅凭恢复包，必须完整恢复全部数据（含归档）。

#### F-06 「可靠备份」与「保证删除」互相矛盾，文档在多处同时承诺了两者

- **证据**：
  - threat-model.md L116 说，事后加锁后「云端底层 PITR 与历史冷备将在保留期满后自然淘汰」；而 sync-protocol.md L224 和 [cloudflare-cloud-architecture.md](../docs/cloudflare-cloud-architecture.md) L143 规划的是「**3 年全量归档**」，归档没有淘汰期。
  - K=5 的 R2 快照含有 `vault_keys` 的 `wrapped_dek`（data-structures.md L296），而 shred 只置空 DO 里的那一行。快照生成周期没有定义，所以「多久之后才真正不可恢复」无从回答。
  - **Lock-Wins**（sync-protocol.md L162）：与 `LOCK` 并发的明文 `UPDATE` 会被保留为冲突分支。
    - 这份明文会存在于各端的 `block_conflicts`（data-structures.md L374 允许 `is_locked=0` 时 `content` 非空）、`sync_ops` 和 DO 中。
    - 加锁方根本不知道这个 `op_id`，没法 purge。
    - SEC-01 只测单设备的顺序流程，覆盖不到这条路径。
  - 瞬态剪贴板声称「绝不应进入 30 天 PITR」（threat-model.md L98），数据结构却把它放进了 DO SQLite 表 `ephemeral_clips`（data-structures.md L526）。SQLite DO 的 PITR 覆盖全部 SQL 数据。
- **第一性原理**：备份的定义就是「**删不掉的副本**」。没有系统能同时保证「随时可恢复」和「随时可彻底删除」，只能选一个默认值并说清楚。
- **建议**：
  - 对一个以「永不丢数」为第一目标的个人工具，默认选择**备份优先**。删除和碎纸只保证「在活跃数据集里不可见」。
  - 明确写出「彻底不可恢复」的时间上界 = max(PITR 30 天, 归档保留期, 快照轮换周期)。
  - 需要真正不留痕的场景，引导用户轮换秘密本身。
  - 顺带收益：一旦不再承诺碎纸，`wrapped_dek` 可以直接放进 `LOCK` op。这样 `vault_keys` 同步表、`MNK1` 信封、`key_seq` 水位、INV-SYNC-4 整套机制都可以删掉（§4）。

#### F-07 T5「密码学级硬隔离」对主动型同 UID 攻击者不成立

- **证据**：threat-model.md L29 和 L148 声称，即使 Web UI 正处于解锁态，被劫持的同 UID Agent 也拿不到加密块的内容。
- **反例**：同 UID 进程可以做下面任何一件事，然后**等你下一次输入 Vault 口令**：
  - 替换用户可写的 `~/.local/bin/mynote`。自升级的 `standalone` 模式恰恰要求二进制用户可写（interface-contracts.md L130）。
  - 在 shell rc 里给 `mynote` 加 alias。
  - 修改 `formatters.toml`。
  - 修改浏览器 profile 或安装恶意扩展。
- **正确表述**：
  - Tier 2 保护的是「**某一时刻的被动读取**」，即读数据库、读 Daemon、读 WAL。
  - 对能**持久化篡改执行环境**的攻击者，任何用户态密码学都无能为力。这是操作系统权限模型决定的，不是实现问题。
- **建议**：
  - 把 T5 的 Tier 2 栏改为「⚠️ 防被动读取；不防持久化篡改」。
  - 补充缓解措施：二进制安装到用户不可写的位置（交给包管理器）；Agent 运行在沙箱、容器或独立 UID 下。
  - 这也是删除自升级子系统（F-14）的另一条理由。

### 3.2 🟠 P1：架构取舍与范围

#### F-08 复杂度与问题规模严重失配

- **数量**：
  - 约 50 个具名机制（见 §4 审计表）；
  - 4 种二进制信封；
  - 7 种 op 类型 × 4 个合并域；
  - 3 套存储 Schema（桌面 SQLite、DO SQLite、IndexedDB）；
  - 2 份服务端语义实现（TS Worker + Rust SimCluster 模型）；
  - 规范约 3,400 行，代码 0 行。
- **规模**：日写入约 0.6 MB；按文档口径，DO 1 GB 可以 4 年不做 GC；全量语料只有 MB 量级。
- **第一性原理**：**复杂度本身就是丢数源**，每一个状态机分支都是潜在的 bug。一个人维护的系统，可靠性上限取决于他能完全理解的代码量（C1）。
- **建议**：设立**复杂度预算**，例如「M1 结束时云端代码 < 500 行，core 的同步部分 < 3k 行」。任何新机制都必须附上触发它的**测量数据**。

#### F-09 自研「因果 DAG + 冲突投影 + `SPAN_PATCH`」：「复杂度只有 CRDT 的 1/5」没有依据

- **证据**：architecture-proposal.md L170。
- **分析**：
  - CRDT 难在**实现**；**使用**成熟库（Loro、Automerge，都有 Rust + WASM 版本）只需要付出集成成本。
  - 当前方案自己实现了：因果 DAG、叶子计算、四个合并域、Update-Wins / Lock-Wins、`RESOLVE`、delta 链与检查点、历史截断处理。这些正是 CRDT 库已经做好、并经过大量测试的部分。
  - 而 SimCluster 要从零证明这些自研逻辑是对的。
- **两条可选路径（详见 §5）**：
  - **路径 γ（建议作为 M1 默认）**：
    - 保留「块级 op + 全量载荷 + 所有版本永久保留」；
    - 冲突就是「同一块出现了多个叶子」，UI 显示为「另一台设备的版本」，由用户合并；
    - 去掉 `SPAN_PATCH`，去掉 Lock-Wins 特例（`LOCK` 就是一个普通的正文版本）。
    - 去掉 `SPAN_PATCH` 之后，现有设计本质上就是 γ，完全满足 G1。
  - **路径 β（用 spike 评估）**：每块一个 Loro 文档，盲中继只存 Loro update 二进制。字符级自动合并、历史、快照与压缩都由库提供。适用前提：你确实需要「两台设备同时改同一块」时自动合并。
- **规模论证**：去掉 `SPAN_PATCH` 的代价是，一个 300 KB 的块 zstd 压缩后每次推送约 30–60 KB。如果对大块把防抖从 500 ms 放宽到 3–5 s，或者只在失焦时推送，日增量仍在 MB 级，远低于任何配额。

#### F-10 路线图：第一个里程碑不解决根本痛点

- M0 不含同步（architecture-proposal.md §7）。M0 结束时，你仍然要靠 Heynote + iCloud 跨端。
- 而 M0 本身包含：按块虚拟化的 CM6 UI、整套 L0–L3 CLI、Heynote 导入、两层格式化、Daemon 鉴权、A3/A4/A5 评测、Plane B 的 B1–B4，以及自动爬山（[eval-framework.md](../docs/eval-framework.md) §9）。这是一个人好几个月的工作量。
- **建议**：第一个里程碑应当是能卸载 Heynote + iCloud 的最小闭环，并且包含 E2EE 同步（§6）。

#### F-11 Heynote 核心手感的两项关键风险被推迟或未验证

- **全局热键**：
  - 100 ms 内唤出是 G2 的硬预算（architecture-proposal.md §3 约束 3）。
  - macOS 的浏览器 App Mode 无法注册全局热键；需要的 Swift 壳被放进了 M3 的「后续按需」。
  - 结果：从 M0 到 M2，macOS 上的体验**不如 Heynote**。
- **按块挂载 CM6**：
  - Heynote 的价值之一在于「一整片连续文本」：可以跨块选择、多光标、跨块撤销、整体查找替换。按块独立的 `EditorView` 天然做不到这些，方案用「不到 150 行的桥接」来覆盖，明显低估了难度。
  - Block-First 是**存储**层面的决策，并不要求 UI 按块拆分 EditorView。单个 CM6 文档 + 原子化、不可编辑的块边界装饰（用 transaction filter 保护边界），同样能避免 Heynote 分隔符被 `dd` 删掉的问题。
- **建议**：动手前做两个限时 spike（各 2–3 天）。
  - 一个对比「单文档」和「按块挂载」两种编辑器方案。
  - 一个验证 macOS 壳。Tauri 在 macOS 上用的是 WKWebView，没有 WebKitGTK 的问题，所以可以「macOS 用 Tauri 壳、Omarchy 用 Chromium webapp」，两者加载同一份内嵌前端资源。

#### F-12 DST 覆盖不到真实的服务端

- SimCluster 在 `mynote-core`（Rust）里模拟服务端；真实服务端却是 TypeScript Worker（cloudflare-cloud-architecture.md §7）。两份实现意味着 **DST 证明的是模型，而不是线上代码**。push 事务、epoch、CAS、GC、purge 全都在 TS 那一侧。
- **建议**：
  - (a) 服务端保持**极薄**，只做幂等追加、分配 seq、按 seq 分页、维护 epoch，其余逻辑全部放在客户端；
  - (b) 用同一套场景，对 miniflare 里运行的真实 Worker 做契约测试；
  - 或 (c) 评估用 `workers-rs` 写中继以共享 Rust 代码（代价是 CF 新 API 支持滞后，文档已提及）。

#### F-13 评测框架（Plane B / 自动爬山 / 统计检验）严重前置

- 45/55/25 题分集、Cohen's Kappa、配对 McNemar 检验、跨模型家族评委、自动爬山——在 CLI 还不存在时**无法执行**，在个人项目里维护成本也远高于收益。
- Plane A（DST、取证擦除、格式化幂等）直接守护 G1/G4，应当**保留并前置**。
- **建议**：
  - Plane B 降级为附录。
  - CLI 稳定后，先用 10 条手写场景配合人工观察。
  - 等出现「Agent 经常用错 CLI」的实际证据，再引入统计框架。

#### F-14 自升级子系统过早

- Ed25519 主备双钥离线签名、包管理器探测、防降级、原子替换、Daemon 热交接、Schema 回滚（interface-contracts.md §2.5）——服务对象只有 1 个用户。
- 它还要求二进制用户可写，这削弱了 F-07 里的防线。
- **建议**：删除这个子系统。发布交给 Homebrew tap、AUR 或 `cargo install`，由包管理器负责完整性校验和回滚。保留「Schema 迁移前用 `VACUUM INTO` 备份」这一条，它便宜且直接服务 G1。

#### F-15 移动端与平台现实中需要核实的点

- **iOS 扫码配对**：
  - 系统相机扫码会在 **Safari** 里打开链接，而不是已安装的主屏 PWA；两者存储隔离，配对数据会落进 Safari。所以 threat-model.md L188 的主流程在 iOS 上走不通。
  - 应当把「粘贴配对码」作为 iOS 主流程，或者在 PWA 内用 `getUserMedia` 自己扫码。
- **WebAuthn RP ID 不能是 IP 地址**：
  - 本地 UI 如果通过 `127.0.0.1` 访问，就用不了 PRF；而且 `localhost` 和 `127.0.0.1` 的 Cookie 互不相通。
  - 建议统一为 `http://localhost:<port>` 这一个入口。
- **Omarchy 上的 PRF**：Chromium 在 Linux 上的平台认证器和 PRF 可用性需要验证，很可能只能依赖支持 hmac-secret 的 FIDO2 安全密钥。
- **WASM 体积预算**：首屏 WASM 不超过 350 KiB（gzip 后），要同时装下 argon2、XChaCha20、blake3、zstd、msgpack 和多个格式化器；`zstd-sys` 编译到 `wasm32` 还需要 C 工具链。需要用 spike 实测。
- **移动端范围**：手机上的真实用法多半是查看、复制和快速追加，未必需要完整编辑器、冲突合并和 Vault 管理。建议第一版 PWA 只做「**读 + 复制 + 追加新块**」。

### 3.3 🟡 P2：文档质量与次要机制

#### F-16 未经测量的数字被写成了事实

- 例子：
  - 「实测体验」（cloudflare-cloud-architecture.md L107）；
  - 「约 300–350 行 TypeScript」（同文件 L58）；
  - 「复杂度只有 CRDT 的 1/5」；
  - 「云端代码量骤减 ~70%」；
  - 「< 15 ms」「< 20 MB」。
- 这些数字都写于同一天，没有任何原型。Worker 实际要实现 push、pull、快照 CAS、R2、vault-keys、瞬态剪贴板、设备配对、WebSocket 休眠、Alarm、归档、GC、限流，300 行不现实。
- **建议**：
  - 每个数字标注来源：**[保证] / [目标] / [估算] / [已测]**。
  - 大量的「100%」「彻底」「绝不」会降低信息密度，审查者分不清哪些是保证、哪些是愿望。

#### F-17 同一概念在多处重复定义，已经出现漂移

- 「5 列盲表」「100 绑定参数规则」「purge 流程」在 ≥ 4 份文档里重复出现。
- AAD 定义已经不一致（F-01）。
- 免费额度的口径也不统一：有的地方写「单 DO 1 GB」，有的写「账户 5 GB」。
- **建议**：每个概念只归属一份文档，其他地方只放链接（单一事实来源）。

#### F-18 元数据泄露与小机制问题

- **元数据泄露**：
  - `vault_key_records.record_id = 'key:<kid>'` 是明文（data-structures.md L518），而且 `key_mutations` 和 `LOCK` 在同一批里提交。
  - 服务端因此能看到「何时加锁或碎纸、一共有多少加密块」，这和「连哪个块被加锁都无法分辨」（cloudflare-cloud-architecture.md L121）的说法不符。
- **分数索引重平衡**（data-structures.md L61）：
  - 两台设备同时对同一窗口重平衡时，逐字段 LWW 会把两套方案交错合并，可能打乱块的顺序。
  - 在个人规模下，64 字节的阈值几乎触发不到。建议**删除重平衡**，允许索引键变长。
- **「4 重独立物理副本」并不独立**（cloudflare-cloud-architecture.md L182）：四份副本都由同一份客户端代码写入，能防硬件故障，防不了逻辑 bug 扩散。

#### F-19 缺少非目标、成功标准和数据可移植性

- 没有「Non-goals」一节。
- 没有可观测的成功指标，例如「连续 N 周日常使用零丢数」「Heynote 已卸载」。
- **数据可移植性比 Heynote 倒退了**：Heynote 是纯文本，新方案是 SQLite + 加密，而只读镜像被放在 M3 的可选项里。
- **建议**：只读 Markdown 镜像同时服务 G1（独立的明文备份）、G5（`rg` / `cat` 直接可用）和反锁定，应当提升为 **M1 默认开启**（加密块仍然只输出占位符）。

## 5. 被低估的替代路径（Build vs Buy）

| 路径 | 描述 | G1 永不丢数 | 复杂度 | 适用条件 |
| --- | --- | --- | --- | --- |
| **α 当前方案** | 自研因果 DAG + 四合并域 + delta 链 + 快照/GC | 依赖大量自研代码都正确 | 高 | — |
| **γ 版本保留式记录库**（推荐 M1 默认） | 块级 op 全量载荷；同一块多个叶子时展示为多个版本；字段 LWW；所有版本永久保留（Atuin 式） | 构造性保证：任何版本都不会被覆盖 | 低 | 同块并发极少，允许人工合并（个人场景成立） |
| **β 每块一个 Loro / Automerge 文档** | 盲中继存 CRDT update；字符级自动合并；历史与压缩由库提供 | 由成熟库保证 | 中（集成成本 + 元数据体积） | 确实需要同块并发自动合并，或想要逐字符的时间旅行 |
| **δ 纯文本文件 + git** | 每块或每个 buffer 一个文件，自动提交并推送到私有仓库 | 有 git 历史兜底 | 低 | 只有桌面；不在乎实时剪贴板；可以接受 git-crypt 级别的加密 |

**结论**：M1 用 γ。在 spike 阶段花 2–3 天评估 β：如果 Loro 的 Rust + WASM 体积和 API 都能接受，它可以同时替掉冲突 UI、`SPAN_PATCH`、时间旅行和快照压缩，长期来看可能更省事。δ 因为移动端和 E2EE 的限制不推荐，但它说明了一点：**纯文本可移植性是值得保留的属性**，所以建议提前做只读镜像（F-19）。

## 7. 文档与过程建议

1. **ADR 状态**：从「已最终拍板」改为「Proposed」，等 spike 证据出来后逐条改为「Accepted」，并记录「被拒方案及理由」。
2. **数字标签**：每个性能、体积、行数、成本数字都标上 [保证] / [目标] / [估算] / [已测]，少用「100%」「彻底」「绝不」。
3. **单一事实来源**：每个概念只在一份文档里定义（线格式 → data-structures.md；协议 → sync-protocol.md；安全 → threat-model.md），总览文档只放链接。
4. **补齐三节**：Non-goals、成功指标、数据可移植性与导出。
5. **规范篇幅预算**：先用代码验证，再按实现回写规范。规范领先代码太多，会产生「精确的错误」。
6. **把恢复当作功能**：「从零恢复」写进 CI，和 DST 同级。

## 8. 需要你拍板的开放问题

1. **移动端定位**：第一版只做「读 + 复制 + 追加」，还是要完整编辑？
2. **删除与备份**：两者冲突时，是否同意默认「备份优先」，删除只保证「活跃数据集不可见」？
3. **冲突体验**：同一块的离线并发编辑，能否接受以「两个版本并列 + 手动合并」呈现？如果需要字符级自动合并，就要认真评估 Loro。
4. **macOS 全局热键**：是否作为第一个可日用版本的必备项？
5. **项目目的**：评测框架和自动爬山是否本身就是学习或研究目标？如果是，「过度建设」可能是有意为之，本报告对 F-13 的判断应相应调整。

## 附录 A：规模粗算

- 日上行：500 ops × 1.2 KB ≈ **0.6 MB/日**，约合 **220 MB/年**，3 年约 660 MB（与文档估算的约 650 MB 一致）。
- 按文档的单 DO 1 GB 口径，不做 GC 可以撑约 **4.5 年**。
- DO 行写：500 × 2 ≈ 1,000 行/日，免费层约 100,000 行/日（约 300 万行/月），占比约 1%。
- 新设备全量 pull（第 1 年末）：约 220 MB。桌面上可以接受；在手机上偏重，这正是「按数据触发引入快照」的依据。
- 大块成本：300 KB JSON 用 zstd 压缩后约 30–60 KB。每天对大块做 50 次全量推送，约 1.5–3 MB/日，仍然在量级之内，所以 `SPAN_PATCH` 可以推迟。
